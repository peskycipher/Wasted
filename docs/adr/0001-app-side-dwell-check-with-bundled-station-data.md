# App-side dwell check with bundled station data

> **Decision (2026-11-07): implemented ahead of approval; deployment gate stands.** The police-station dwell trigger remains "design only, not approved for deployment" per `portal/docs/ciphercell-brief.md` and is on the lean spec's retired-additional-triggers list (spec #59) — its module map was closed there, while this repo continues to build and test the implementation. Status recorded because portal and this repo had drifted silently. Consequences: no marketing copy may feature this trigger (portal `PRODUCT.md` retire-list); release gates on the portal-side privacy/policy review (#36, #37, #40, #41), not on this implementation being complete;

The Geoscience Australia `POLICING_FACILITY` layer has ~1,569 points, but Android's `GeofencingClient` caps registered fences at 100, so OS geofencing cannot express "all Australian police stations". We instead run the trigger ourselves: a foreground service takes a fused-location fix every 2 minutes and computes the dwell state machine (enter/leave the 50 m fences, fire after N minutes of continuous dwell) in-process against a snapshot of the facilities bundled into the APK at build time by `scripts/gen-police-stations.py`. Bundling was chosen over runtime fetching because the wipe must work offline and with the network unavailable — exactly when the trigger matters — and because it keeps the device from identifying itself to the GA service. Cost: the dataset can go stale until someone re-runs the generator script, and the app pays for a periodic location fix (one every interval) rather than platform-efficiency geofencing.
